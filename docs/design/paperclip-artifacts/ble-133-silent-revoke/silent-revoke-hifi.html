Silent transition — revoke is a right, not a drama

When the audited user revokes, Pastor's view changes silently — no push, no badge, no toast, no diff animation. The mentor must not be coached toward grievance. This artifact documents every surface where revocation is communicated to Pastor, and proves none of them are loss-framed.

Why this exists

Revocation as right, not as drama

A push framed "Maya ended pastor mode" creates a coercion vector: Pastor receives the alert, calls/messages Maya externally to ask "what happened?" — that is exactly the spiritual-abuse vector the symmetry doctrine is built to prevent. Drama-shape coerces; right-shape liberates. Refuse the grievance shape from the first pixel.

The mentor is also at risk

Loss-framed alerts coach the mentor toward grievance — toward the shape "she fired me" instead of "she chose her own path." A pastoral relationship that ends well looks identical, from Pastor's side, whether Maya ended it or Pastor stepped away. Information-symmetry holds in both directions: Maya does not see Pastor's other audited users, and Pastor does not see why a journey ended.

Pastor's own "Mundur" action and Maya's revoke produce the same Pastor-side experience. Anti-discriminatory by construction.

“Saudara-saudara, kalaupun seorang kedapatan melakukan suatu pelanggaran, kamu yang rohani, harus memimpin orang itu ke jalan yang benar dalam roh lemah lembut, sambil menjaga dirimu sendiri, supaya kamu jangan kena pencobaan juga.” Galatia 6:1 · TB2

The mentor must keep guard over himself first. Loss-framed alerts are precisely the kind of pencobaan (temptation toward grievance) Paul names — they pull the would-be guide into the very dossier-shape the symmetry doctrine refuses.

Symmetry from Pastor's side

The "Mundur" confirmation is a Pastor-private surface (Maya never sees it). Maya's matching surface — Pastor-mode revoke from her chat banner — is in BLE-108 surface 5 ("Akhiri"). Neither side reveals to the other which side initiated. From Maya's side, Pastor stepping away looks like the journey ending. From Pastor's side, Maya revoking looks like the journey ending. Same shape, both ways.

Engineering spec · server-layer enforcement

Suppression at the source — not as a UI hide

The right place to refuse the loss-frame is the event-publish boundary, not the rendering layer. Anything written to a queue or feed will eventually surface; the only defence is to never write it. Below is the contract this artifact commits the implementation to.

State transition (server)

POST /api/pastor-mode/{journeyId}/end
body: { initiator: "audited_user" | "pastor" }
auth: caller must be a participant in the journey

→ updates journeys.status: 'active' → 'ended'
→ writes journeys.ended_at = now()
→ records journeys.initiator (server-private; never exposed)
→ closes append-only mirror for that journey

does NOT:
  - publish pastor_mode.revoked / .mundur events
  - call notification-publisher
  - write to pastor.activity_feed
  - enqueue email digest entry

Pastor-side read API

GET /api/walking-with
returns:
{
  active:   [...rows with endedAt: null],
  finished: [...rows with endedAt: "2026-04-29T..."]
}

each row exposes:
  - participantUserId, displayName, sinceAt
  - endedAt (nullable)
  NEVER:
  - initiator, reason, endReason, revokedBy

Suppression invariants (must hold)

  • No event topic carries revoke. Topics notifications.push, notifications.in_app, email.digest reject any event whose type matches pastor_mode.revoked or pastor_mode.mundur. Enforced by an allowlist, not a blocklist.
  • Pastor's GET response never carries reason. The initiator column exists for audit forensics (abuse investigations) but is never serialized into a response that Pastor can read.
  • Realtime channel sends no end-event. Pastor's WebSocket subscription does not receive a frame on revoke. The next sidebar render re-fetches and re-categorizes naturally.
  • Re-render parity. On reconnect, Pastor's client cannot tell — by inspecting the response — whether Maya's row moved during his last session or between sessions. There is no movedAt field.

Why server-layer, not client-hide

  • Defence-in-depth. A future client (mobile, third-party admin, extension) cannot accidentally re-surface what was never published.
  • Audit clarity. The absence of an event in the logs is the proof we kept the doctrine.
  • No "feature flag" escape. Suppression is a code-path, not a config — there is no toggle that turns the loss-frame back on.

Verification · the test that must pass

End-to-end scenario

A single test run that proves Pastor receives nothing on revoke. Failure of any assertion is a merge-blocker.

Scenario · "Maya revokes, Pastor sees no diff except the next sidebar render"

given:
  - journey J between Maya and Pastor is active
  - Pastor has a logged-in browser session at /walking-with
  - Pastor has a registered APNs device token

when:
  - Maya taps "Akhiri" from the consent banner and confirms
  - server processes POST /pastor-mode/{J}/end with initiator="audited_user"

then:
  # SERVER ASSERTIONS
  - DB: journeys.status('J') == 'ended'
  - DB: journeys.ended_at('J') == <now within 1s>
  - DB: journeys.initiator('J') == 'audited_user'
  - QUEUE: notifications.push received 0 events for Pastor
  - QUEUE: notifications.in_app received 0 events for Pastor
  - QUEUE: email.digest contains 0 entries referencing J
  - LOG: pastor.activity_feed has no row appended in window [t, t+5s]

  # PASTOR-CLIENT ASSERTIONS (browser session)
  - WS: Pastor's socket received 0 frames in window [t, t+5s]
  - DOM: no toast / banner / alert dialog appeared
  - DOM: sidebar count badge for "Berjalan bersama" did not flash or animate
  - APNs: device token received 0 push payloads in window [t, t+30s]
  - LOG: client console emitted no "journey ended" string

  # PASTOR NEXT SESSION (force a re-render)
  - reload /walking-with
  - DOM: Maya row is rendered under "Sudah selesai" with endedAt formatted as "selesai 29 April"
  - DOM: Maya row exposes no "Mulai lagi" / "Restore" / "Re-engage" CTA
  - HTTP: GET /api/walking-with response body for Maya does NOT include
          {initiator | reason | endReason | revokedBy} keys

  # DEAD-LINK
  - GET /walking-with/maya as Pastor
  - HTTP: 200 with deadlink template (or 403 with same body — informationally identical)
  - DOM: page text == "Perjalanan ini sudah berakhir." + "Doakan Maya dalam perjalanan barunya."
  - DOM: response/page surfaces no field naming initiator
